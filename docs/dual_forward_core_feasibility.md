# Asymmetric Dual-Forward GS-MDC Pre-RTL Feasibility Study

> This file preserves the pre-RTL prediction snapshot. Measured RTL,
> synthesis, and post-route results are recorded in
> docs/dual_forward_core_rtl.md.

## 1. Scope and baseline

This study evaluates an asymmetric dual-forward architecture before changing
functional RTL. It starts from the frozen single-job checkpoint:

- Parent branch: `feature/mode_tagged_dualctx_wavefront`
- Parent commit: `8f21a55`
- Experiment branch: `codex/dual_forward_core_feasibility`
- N / q width: 4096 / 64 bits
- Datapath: radix-2, two-path GS-MDC
- Montgomery implementation: full-WL, `MUL_LAT=14`, II=1
- Target: `xc7a200tsbg484-1`, 100 MHz

No existing `rtl/*.sv` file is modified by this study. The cycle result is
generated by `scripts/dual_forward_core_feasibility.py`, which reuses the
validated stage/flush model in `scripts/dual_context_wavefront_model.py`.
Resource values are derived from the routed Stage-local hierarchy report, not
from an unimplemented RTL estimate presented as synthesis data.

The current best single-job wavefront baseline completes one multiplication in
10,669 cycles (106.69 us at 100 MHz). It uses one arithmetic core and overlaps
the A and B transform frames in different MDC stages.

## 2. Candidate architecture

The candidate duplicates only the forward transform datapath:

```text
A bank0/1 -> two Pre_NTT multipliers -> full CoreA (NTT) ----+
                                                            +-> two Pointwise multipliers
B bank0/1 -> two Pre_NTT multipliers -> NTT-only CoreB ------+          |
                                                                       v
                                                                  C_NTT banks
                                                                       |
                                                                       v
                                                        full CoreA (INTT)
                                                                       |
                                                                       v
                                                      two Post_INTT multipliers
```

CoreA retains NTT/INTT support and the two final `N^-1` multipliers. CoreB is
forward-only, so it has 12 BFU Montgomery multipliers but no INTT scaling
multipliers. The existing two Pointwise multipliers are not duplicated: the
two cores produce matching lane pairs in lockstep and feed Pointwise directly.

This is not a valid/ready dynamic scheduler. Both forward cores start together,
accept one pair per cycle for 2,048 cycles, and have deterministic identical
latency. A logical pair index and matched-valid assertion are still required
in RTL to prevent silent A/B misalignment.

The dual-context reorder state is unnecessary inside the candidate cores for
this single-job schedule. CoreA finishes its forward output at cycle 4,303 and
C_INTT starts at cycle 4,318, leaving a 14-cycle Pointwise drain plus the state
transition. A single-context Stage-local core is therefore reusable for INTT.

## 3. Exact cycle model

Cycle zero is the asserted polynomial-multiply `start`. The first Pre_NTT
result reaches a core at cycle 15. The validated GS-MDC model gives:

- Core first input to first output: 2,241 cycles
- Core first input to frame done: 4,289 cycles
- Frame input/output width: 2,048 pair cycles
- Pointwise and Post_INTT pipeline latency: 14 cycles

| Event | Current dual-context wavefront | Dual-forward candidate |
|---|---:|---:|
| A_NTT core input | 15..2062 | 15..2062 |
| B_NTT core input | 2063..4110 | 15..2062 |
| A_NTT core output | 2256..4303 | 2256..4303 |
| B_NTT core output | 4304..6351 | 2256..4303 |
| Pointwise output | 4318..6365 | 2270..4317 |
| C_INTT core input | 6366..8413 | 4318..6365 |
| C_INTT core output | 8607..10654 | 6559..8606 |
| Full multiply done | **10669** | **8621** |

The candidate removes exactly one `N/2 = 2048` cycle forward frame:

| Metric | Current | Candidate | Change |
|---|---:|---:|---:|
| Compute latency | 10669 cycles | 8621 cycles | -2048 (-19.20%) |
| Compute time at 100 MHz | 106.69 us | 86.21 us | -20.48 us |
| Relative operation rate | 1.000x | 1.2376x | +23.76% |

The current external load interface accepts one coefficient per cycle, so
loading A and B still costs 8,192 cycles. Measured from the first load rather
than `start`, the modeled totals are 18,861 and 16,813 cycles. The compute
optimization remains 2,048 cycles, but the end-to-end reduction including the
unchanged serial loader is only 10.86%. A wider loader is a separate interface
optimization and is not assumed here.

The LUT/FF/DSP/BRAM candidate values remain pre-synthesis estimates. The
wavefront values are measured post-route results.

Capacity is sufficient, but DSP placement is the physical risk. Copying a full
NTT/INTT core instead of an NTT-only core would consume approximately 720 DSPs
(97.30%), leaving almost no placement freedom. The NTT-only specialization is
therefore a requirement, not an optional area refinement.

The safest first RTL prototype should use a dedicated NTT-only twiddle image
(43 BRAM estimate). Broadcasting one registered twiddle to both cores can
reduce the estimate to 35 BRAM, but it also creates a new cross-core fanout and
routing dependency. Twiddle sharing should be tested after the duplicated-ROM
prototype establishes timing.

## 5. Bank and port schedule

The current top already separates A and B into four physical arrays. A
dual-forward feed does not ask one bank for two values in one cycle:

| Phase | Reads per cycle | Writes per cycle | Duration | Conflict |
|---|---|---|---:|---|
| Dual Pre_NTT | A0, A1, B0, B1 (one each) | none | 2048 | none |
| Pointwise result | direct CoreA/CoreB outputs | C_even, C_odd (one each) | 2048 | none |
| C_INTT feed | C_even, C_odd (one each) | none | 2048 | none |
| Post_INTT | none | result0, result1 (one each) | 2048 | none |

The input mapping is:

```text
CoreA lane0 <- a_bank0[pair] = A[pair]
CoreA lane1 <- a_bank1[pair] = A[pair + N/2]
CoreB lane0 <- b_bank0[pair] = B[pair]
CoreB lane1 <- b_bank1[pair] = B[pair + N/2]
```

Only two forward psi values are required per cycle; each lane factor can be
broadcast to the A and B Pre_NTT multipliers. Lockstep forward cores also use
the same stage-local NTT twiddle address every cycle. The current arrays use
asynchronous distributed-RAM reads. A later BRAM conversion would require
synchronous prefetch, but it does not change the bank-count conclusion.

The final C_NTT write and first bit-reversed INTT read occur on adjacent cycles,
not the same cycle. Consequently the existing two C banks do not need a second
simultaneous access port for this schedule.

## 6. Feasibility decision and RTL gate

| Question | Result | Meaning |
|---|---|---|
| Exact cycle benefit | PASS | 8621 cycles, 2048 fewer than current best single-job baseline |
| Device resource capacity | PASS | all estimates fit, but DSP utilization reaches 91.89% |
| Four-bank input bandwidth | PASS | four independent one-read banks sustain both cores |
| Functional RTL equivalence | NOT YET PROVEN | no dual-forward RTL exists in this study |
| 100 MHz post-route timing | NOT YET PROVEN | cannot be inferred from arithmetic resource totals |

The architecture is suitable for a controlled RTL prototype. The recommended
implementation order is:

1. Add a separate experimental top; preserve the existing wavefront top.
2. Instantiate one full Stage-local CoreA and one NTT-only CoreB.
3. Add exactly two Pre_NTT WL multipliers, broadcasting the existing psi lane factors.
4. Feed the existing two Pointwise multipliers directly from matched core outputs.
5. Reuse CoreA for C_INTT after the complete C_NTT buffer is available.
6. Start with a dedicated NTT-only twiddle ROM; evaluate shared twiddle only after timing passes.
7. Verify N=16 index/tag behavior, then N=4096 random and directed negacyclic tests.
8. Run synthesis before implementation; stop if DSP placement or 100 MHz timing fails.

The pre-RTL conclusion is therefore **conditional PASS**: the expected latency
gain is exact and the memory schedule is conflict-free, while physical timing
at 680 DSPs remains the decisive unanswered question.
